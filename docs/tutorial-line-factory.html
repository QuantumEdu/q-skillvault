La Forma Simple: Fábricas Issue-to-PR

Cómo operar y construir fábricas de software autónomas mediante un loop determinista FSM, aislamiento de procesos, Git Worktrees y control loopback con GitHub como control plane.

Nivel: Intermedio — Avanzado
Tiempo estimado: 40 minutos
Paradigma: Deterministic State Machine (FSM)
Stack: Go, SQLite, GitHub CLI, Git Worktrees, ntfy
🎯 Competencia Principal a Adquirir Al finalizar este tutorial serás capaz de diseñar, implementar y operar un pipeline agentico determinista (Issue → Plan → Build → Review → Wait CI / Repair → Ready) desacoplando la inteligencia del LLM del control de flujo, garantizando cero alucinaciones de contexto y eliminando colisiones en el árbol de trabajo.

0. Diagnóstico Inicial & Prerrequisitos

Antes de arrancar, validemos que el terreno esté firme. Responde mentalmente este autochequeo:

1. Git Worktrees

¿Sabes por qué ejecutar un agente que escribe código en tu checkout activo de git es un riesgo operacional grave?

Ver explicación

Un agente descontrolado puede pisar archivos sin commitear, desatar conflictos con tu trabajo en progreso o dejar ramas rotas. Un worktree aislado le da un directorio separado que comparte el almacén de objetos .git sin tocar tu working tree.

2. Sesgo de Confirmación

¿Por qué un agente que escribió el código NUNCA debe ser el mismo que lo revisa en la misma conversación?

Ver explicación

En la misma sesión de chat, el modelo retiene sus propios supuestos y justificaciones previas ("yo hice esto por X"). Un evaluador independiente requiere un proceso limpio con banderas y modelo dedicados sin historial previo.

3. Estado en el Loop

¿Dónde debe residir la máquina de estados: en el prompt del LLM o en código estricto compilado?

Ver explicación

En código estricto compilado (Go/Python). El LLM sólo recibe el prompt de la fase actual y devuelve un JSON unificado. El código decide si avanza, repara o pide ayuda.

1. La Filosofía de "La Forma Simple"

La industria del software agentico se saturó de arquitecturas hipertrofiadas: grafos gigantes con 50 herramientas simultáneas, agentes charlando en bucles infinitos y árboles de decisión impredecibles. La forma simple destruye esa complejidad.

La Arquitectura Original (Captura Canónica)

"Un loop en Go o Python. Estado en un JSON (o en un comentario del issue). El modelo no ve el grafo entero."

❌ El Mega-Grafo Monolítico
  • El modelo carga con 50 turnos de chat en su ventana de contexto.
  • Alucinación de herramientas y confusión de roles ("ahora soy coder, ahora reviewer").
  • Si un test falla, el agente entra en pánico y edita archivos irrelevantes.
  • Costo de tokens desbocado sin presupuesto de reparación.
✅ La Forma Simple (FSM Line)
  • Procesos limpios: Cada fase es una ejecución nueva e independiente.
  • El modelo no ve el grafo entero: Sólo ve las variables necesarias (PromptVars) de la fase actual.
  • Contrato JSON unificado: Termina en ok, needs_human o blocked.
  • Presupuesto estricto: Máximo 3 reparaciones de CI antes de detenerse.

2. Anatomía del Loop Fase a Fase

A continuación desglosamos qué entra, qué se ejecuta y qué sale en cada estación de la fábrica:

0

Fase 0: El Issue de GitHub (El Gatillo)

GitHub Control Plane

Todo comienza en un Issue. No en una orden verbal ni en un chat efímero. El issue es auditable, permite adjuntar capturas, requisitos y referencias de tickets anteriores.

GitHub Issue #101markdown
# feat(pos): soporte para escaneo offline y tickets térmicos

## Contexto
El sistema POS actual requiere conexión constante a la API central.
Necesitamos operar localmente ante caídas de red y emitir tickets ESC/POS.

## Criterios de Aceptación
1. Lector de código de barras procesa EAN-13 en memoria local (SQLite).
2. Cálculo de subtotal con desglose de IVA (16%) incluido.
3. Generación de payload de impresión térmica ESC/POS.
4. Cobertura de tests unitarios mínima del 90%.
1

Fase 1: PLAN (Diseño y Clasificación)

agent: plan read-only

El factory inyecta el issue y el repo en prompts/plan.md. El agente inspecciona el repositorio en modo lectura (sin modificar ningún archivo). Diseña la arquitectura y enumera las tareas.

Contrato de Salida (Plan Aprobado)json
{
  "status": "ok",
  "summary": "Diseño completado: tabla sqlite local_inventory, motor TaxCalculator y formatter ESC/POS con 4 tareas unitarias."
}
Bifurcación: Intervención Humana (Needs Human)json
{
  "status": "needs_human",
  "question": "¿Los precios de los productos en la base local ya incluyen IVA o el 16% se adiciona al subtotal en caja?"
}
🛑 El Freno de Emergencia: needs_human Si el modelo detecta ambigüedad comercial o técnica, emite needs_human y el factory se detiene de inmediato. Envía una notificación push a tu teléfono y espera tu respuesta con line continue --answer "...".
2

Fase 2: BUILD (Implementación en Worktree Aislado)

isolated git worktree code & test

Line crea un Git Worktree independiente en ../kbs-worktrees/job-<id>. El agente trabaja exclusivamente en ese directorio, escribe el código, crea las pruebas, corre go test, commitea en una rama limpia y crea el Pull Request con gh pr create.

Contrato de Salida (Build)json
{
  "status": "ok",
  "summary": "Implementados BarcodeReader, TaxEngine y ESCPOSFormatter con 12 tests unitarios pasando.",
  "pull_request": "https://github.com/QuantumEdu/pos-app/pull/102",
  "head_sha": "d4e8c1a9f023"
}

El factory extrae pull_request y head_sha y los guarda de forma persistente en SQLite.

3

Fase 3: REVIEW (Evaluación Independiente)

independent reviewer audit gate

Aquí se rompe el sesgo del autor: se despacha un proceso nuevo con el flag --review-exec (por ejemplo, Claude con temperatura 0.1 o un modelo auditador). El revisor recibe el diff del PR y verifica contratos de seguridad, tipado y cobertura.

Contrato de Salida (Review)json
{
  "status": "ok",
  "summary": "Revisión aprobada: no hay llamadas bloqueantes a red en el flujo offline, cobertura 94%, tipos estrictos."
}
4

Fase 4: WAIT_CI & El Loop de REPAIR

continuous polling github actions

Line sondea continuamente gh pr checks (cada 10s hasta 20m):

  • Todos los checks pasan (PASS): El job transiciona directamente a READY.
  • Algún check falla (FAIL): Se incrementa repair_count. Si no supera el presupuesto (3), transiciona a REPAIR.
Fase REPAIR (Corrección Quirúrgica)agentic loop

El agente de reparación recibe el detalle exacto del log de CI que falló (ej: "FAIL: TestTaxRounding - expected 116.00 got 115.99"), corrige el cálculo en el worktree, commitea, pushea y el factory vuelve automáticamente a REVIEW y WAIT_CI.

5

Fase 5: READY (Entrega Limpia)

ready for human merge

Al confirmarse el éxito de CI:

  1. El factory destruye automáticamente el worktree temporal para liberar disco.
  2. Envía notificación push final: "Job listo para merge con PR #102 aprobado y CI verde".
  3. El humano hace el merge en GitHub. Cero esfuerzo de micro-management.

3. Caso Práctico Extendido: El Sistema POS

Veamos una corrida completa simulada sobre un sistema de punto de venta (POS) para observar cómo interactúan la terminal, los prompts y el humano:

1. Lanzamiento del Factorybash
terminal
line run   --repo $HOME/dev/pos-app   --auto   --review-exec claude   --review-exec-arg --temperature=0.1   --ntfy-topic line-pos-alerts   https://github.com/QuantumEdu/pos-app/issues/101

Salida en tiempo real del CLI:

job 4a8f9021c7e2
issue https://github.com/QuantumEdu/pos-app/issues/101
phase plan
status needs_human
question ¿Los precios leídos por el escáner ya tienen IVA (16%) incluido o debe sumarse al total?

El factory se pausó de forma segura. El desarrollador recibe la alerta en el celular o la ve en su terminal y responde:

2. Continuación con la respuesta humanabash
terminal
line continue --answer "Vienen con IVA incluido, calcular el desglose: base = precio / 1.16"

Evolución Automática (Auto-Advance Loop):

  1. plan finaliza con ok: diseña TaxCalculator.Split(grossPrice).
  2. build arranca en $HOME/dev/pos-app-worktrees/job-4a8f9021c7e2. Escribe pkg/tax/tax.go y pkg/tax/tax_test.go. Abre PR #102.
  3. review ejecuta el evaluador independiente con --temperature=0.1. Emite ok: tests cubren casos borde de redondeo bancario.
  4. wait_ci sondea GitHub Actions. A los 45s: Pass (14 checks verdes).
  5. Worktree eliminado automáticamente. Status final: READY.

4. Caso Real: La Implementación del Propio Line en KBS

Este tutorial no es teórico: acabamos de aplicar exactamente este flujo para resolver el backlog completo de 11 issues (#77 a #87) en el repositorio kbs con SDD:

Issue Módulo Problema Detectado Solución Aplicada en el Factory
#86 internal/cli SysProcAttr.Setsid rompía compilación en Windows. Aislamiento mediante build tags _unix.go y _windows.go.
#80 internal/line Agentes escribían sobre el checkout sucio del operador. Implementación de GitWorktreeManager en worktree.go.
#79 internal/line Build y Review compartían el mismo contexto de agente. Flags --review-exec y despacho desacoplado en fase review.
#77 internal/line Requería ejecutar line next manualmente en cada fase. Bucle AutoAdvance con detención estricta en needs_human.
#78 internal/line wait_ci sólo hacía un intento y salía. Bucle continuo de polling (10s/20m) con transición a repair.
#83 internal/line La UI web no permitía originar jobs nuevos. Formulario POST /jobs/new con binding loopback (127.0.0.1).
#84 internal/line ntfy sólo era de salida, sin poder continuar desde móvil. Cabecera Actions con botones interactivos para continuar.

5. Manual de Comandos de Line

Referencia canónica de la CLI de line:

line run

Inicia un nuevo job a partir de un issue de GitHub.

line run --repo <path> [flags] <issue-url>

Flags principales:
  --auto           Auto-avanza fases (def: true)
  --exec <cmd>     Ejecutor autor (def: claude)
  --review-exec    Ejecutor revisor independiente
  --worktree       Aísla en git worktree (def: true)
  --ntfy-topic     Tópico de ntfy para alertas

line status

Muestra el estado del último job o de un job específico.

line status [job-id]

Salida:
  job <id>
  issue <url>
  phase <plan|build|review|wait_ci|ready>
  status <running|awaiting_next|needs_human|ready>
  events timeline...

line continue

Desbloquea una fase en estado needs_human.

line continue --answer "<texto>" [job-id]

Ejemplo:
  line continue     --answer "Usar PostgreSQL en vez de MySQL"

line serve

Levanta el panel de control web loopback.

line serve [--listen 127.0.0.1:7340]

Características:
  - Enlace exclusivo a 127.0.0.1 (seguridad)
  - Creación de jobs desde el navegador
  - Respuesta a needs_human con formulario

6. Gestión de Proyectos Multi-Repo (#89)

Cuando operas en organizaciones reales con monorepos, múltiples microservicios o repositorios satélite (ej. frontend web, backend API, librerías compartidas), una herramienta que te obligue a tipear --repo /ruta/completa/al/checkout en cada invocación añade fricción operativa y propicia errores humanos.

Para resolver esto de raíz, line incorpora un subsistema de gestión de proyectos persistido directamente en SQLite. Puedes registrar múltiples proyectos, asociarles ejecutores y tópicos de notificación específicos, y conmutar el foco activo con un solo comando:

Registro y Conmutación de Proyectos

terminal
# 1. Registrar tu proyecto principal (se activa automáticamente)
line project add pos-core \
  --name "POS Core Engine" \
  --repo $HOME/dev/pos-app \
  --exec claude \
  --ntfy-topic pos-alerts

# 2. Registrar un segundo repositorio (frontend web)
line project add web \
  --name "Web Dashboard" \
  --repo $HOME/dev/web-dashboard

# 3. Listar proyectos registrados (* marca el activo)
line project list

# 4. Cambiar el proyecto activo
line project use web

# 5. Ver el proyecto activo actual
line project current

⚡ Resolución Automática en line run

Gracias a la tabla projects en SQLite, cuando ejecutas line run omitiendo el flag --repo:

  1. line consulta el proyecto con is_active = 1.
  2. Hereda automáticamente repo_path para montar los worktrees.
  3. Hereda el ejecutor autor (--exec) y de revisión (--review-exec) predeterminados.
  4. Hereda el tópico de notificaciones ntfy (--ntfy-topic).
Ejecución directa sin fricciónbash
terminal
# ¡Basta con pasar la URL del issue!
line run https://github.com/QuantumEdu/pos-app/issues/105

📱 Notificaciones ntfy en tu Celular

Al configurar export LINE_NTFY_TOPIC=mi-topico-secreto, tu teléfono recibe una alerta sonora cuando el factory requiere decisión humana.

Gracias a la cabecera Actions, la notificación incluye botones rápidos:

🔒 Por qué strictly loopback (127.0.0.1)

line serve jamás debe exponerse a 0.0.0.0 ni a internet. El factory ejecuta código shell y compila binarios locales. Si se abriera a la red local sin autenticación, cualquier host podría inyectar comandos remotos.

Line incluye validación estricta en ListenAndServe que rechaza cualquier binding que no sea 127.0.0.1 o localhost.

10. Antipatrones Fatales en Fábricas de Agentes

Antipatrón 1: Permitir que el LLM decida si avanza o no de fase

Por qué falla: Los modelos sufren de fatiga o complacencia. Pueden decidir que "el código ya está bien" sin correr los tests.

La solución de Line: La FSM en Go obliga a ejecutar la fase wait_ci. No hay estado ready sin un exit code 0 de GitHub Actions.

Antipatrón 2: Un solo modelo haciendo de autor y revisor en la misma sesión

Por qué falla: Si el modelo introdujo un bug de lógica, en el review dirá que la lógica es sólida porque recuerda su razonamiento previo.

La solución de Line: Subproceso fresco con --review-exec y temperatura distinta. El revisor sólo ve el diff, no el chat anterior.

Antipatrón 3: Reparación sin presupuesto (Infinite Repair Loops)

Por qué falla: Si un test de CI falla por un problema de infraestructura externa (ej. base de datos caída), el agente intentará parchar el código 50 veces quemando cientos de dólares.

La solución de Line: Presupuesto inquebrantable de maxRepairs = 3. Al 4to intento pasa a BLOCKED y avisa al humano.

Antipatrón 4: Trabajar en el árbol principal de git

Por qué falla: El agente genera cambios sin commitear mientras tú estás editando otro archivo, provocando conflictos de merge y pérdida de trabajo.

La solución de Line: Git Worktrees aislados en directorios hermanos que se limpian al terminar.

11. Rúbrica Metacognitiva & Cierre

Criterio Novato Competente Experto
Arquitectura de Flujo Lanza un mega-prompt esperando que el agente resuelva todo de golpe. Utiliza un pipeline por fases pero con el mismo agente y en el mismo checkout. Implementa FSM en código compilado, con subprocesos limpios, worktrees y review independiente.
Gestión de CI & Errores Ignora el CI local y pushea directo a main sin verificar. Revisa manualmente el CI y le pide al agente que intente otra vez. Loop de sondeo continuo con auto-reparación presupuestada y fallback a BLOCKED.
Intervención Humana Permite que el agente invente requisitos comerciales cuando tiene dudas. Interrumpe al agente deteniendo el proceso completo en la terminal. Utiliza needs_human con notificaciones push interactivas en móvil sin perder el estado.
🔭 Lo Que No Estás Viendo Todavía (Próximos Pasos)

La fábrica `line` está diseñada para automatizar la carpintería pesada (código, tests, PRs, CI). Sin embargo, el merge final siempre lo hace un humano. En sistemas complejos de misión crítica, nunca automatices el clic de `merge to main`: mantén el juicio humano como el último filtro de entrega.
